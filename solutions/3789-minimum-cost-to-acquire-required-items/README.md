# 3789. Minimum Cost to Acquire Required Items

- Difficulty: Medium
- Topics: Greedy, Math
- Language: C++
- 题目链接: https://leetcode.cn/problems/minimum-cost-to-acquire-required-items/

## 题目

有三种物品：类型 1 单价 `cost1`、只满足类型 1 的需求 1 个单位；类型 2 单价 `cost2`、只满足类型 2；类型 3 单价 `costBoth`、同时满足两类各 1 个单位。要求类型 1 的总需求至少 `need1`、类型 2 至少 `need2`，求最小总花费。`1 ≤ cost* ≤ 10⁶`，`0 ≤ need* ≤ 10⁹`。

## 我的思路

- 核心思想：**只有组合包（类型 3）能让两类需求共享一份钱**，所以最优方案里组合包的数量 `k` 一定卡在「边界」上，只可能是三种形态之一，逐一算出来取最小即可。
  1. `k = 0`：两类各买各的单品 —— `need1 × cost1 + need2 × cost2`。
  2. `k = max(need1, need2)`：组合包直接买到满足需求大的那一侧，多出来的那部分对另一类算白送 —— `costBoth × max(need1, need2)`。
  3. `k = min(need1, need2)`：组合包只买满需求少的那一侧，差额用**需求较大那类**的单品补齐 —— `costBoth × min + (max − min) × (need1 > need2 ? cost1 : cost2)`。
- 为什么三种就够：把组合包数量从 `0` 往大调时，只要 `costBoth < cost1 + cost2`，多买一个组合包（同时替掉一个类型 1 和一个类型 2）就严格更省，所以最优的 `k` 会一路顶到某个边界；一旦超过 `min(need1, need2)`，多出来的组合包只服务需求大的那一类，是否继续买取决于 `costBoth` 与那类单品价的比较——同样是取到边界为止。于是 `k` 只可能落在 `0`、`min`、`max` 三个点上。
- 关键变量：`1LL *` 的强制提升。`need` 到 `10⁹`、`cost` 到 `10⁶`，单类花费能到 `10¹⁵`，必须用 `long long`。
- 为什么能够得到正确答案：三种候选覆盖了「组合包数量取边界」的全部情况，而中间值永远不会优于边界值（如上），故三者取最小即全局最优。

## 代码

```cpp
// 3789. Minimum Cost to Acquire Required Items
// 会跨类型省钱的只有「组合包」，所以最优解只可能是三种形态之一：
// 全部买单品类、组合包买到够需求大的那类、组合包买满需求小的那类再多补单品。
class Solution {
public:
    long long minimumCost(int cost1, int cost2, int costBoth, int need1, int need2) {
        return min(
            // 一、两类需求各买各的单品
            1LL * need1 * cost1 + 1LL * need2 * cost2,
            min(
                // 二、组合包直接买到满足较多需求的那一侧（多出来的那部分算白送）
                1LL * costBoth * max(need1, need2),
                // 三、组合包只买满需求较少的一侧，差额用需求较大那类的单品补齐
                1LL * costBoth * min(need1, need2) +
                    1LL * (max(need1, need2) - min(need1, need2)) * (need1 > need2 ? cost1 : cost2)));
    }
};
```

## 代码分析

- 正确性：正确。本机与暴力解对拍（枚举组合包买 `0..max(need1, need2)` 个，其余各买单品，取最小）5000 组随机数据（`cost ≤ 20`、`need ≤ 10`）零差异；官方三个样例 3 / 22 / 0 全部复现；上界 `need = 10⁹、cost = 10⁶` 实测得 `10¹⁵`，`long long` 内不溢出。
- 关键实现：每个乘积都先 `1LL *` 再乘，否则 `need1 * cost1` 在 `int` 里就会溢出（`10⁹ × 10⁶ = 10¹⁵` 远超 `2.1 × 10⁹`）。第三种候选的「差额部分」用的是 `need1 > need2 ? cost1 : cost2`，即需求大的那一类的单价，方向别写反。
- 潜在 Bug：无。注意第三种候选在 `need1 == need2` 时退化成方案二（差额为 0），与 `>` 的严格比较配合是正确的——此时用哪个单价都无所谓。
- 可以改进的地方：把三个候选先算成具名变量（`allSingle` / `allBoth` / `mixed`）再取 `min`，可读性会好很多；本题写法等价、`0 ms` 通过，只是纯表达式嵌套在以后复查时不好读。

## 复杂度

- 时间复杂度：O(1)，常数次乘法与比较。
- 空间复杂度：O(1)。

## 易错点

- **`int` 溢出**：`need × cost` 最大 `10¹⁵`，不写 `1LL *` 就一定挂。这类「答案量级明显超过 2³¹」的题，返回值也常是 `long long`，签名里已经是 `long long` 就别再在中间用 `int` 兜。
- **只考虑两种方案**：只算「全买单品」和「全买组合包」是常见漏解——`costBoth` 比某一类单品便宜、但比另一类贵时，最优是混合方案（组合包买满需求少的一侧再补单品）。
- **补差额时选错单品**：差额只能由需求**更大**的那一类来补，选错就变成给需求已经满足的那类多买东西，方案不可行。
- **`need = 0`**：两侧都为 0 时答案为 0；单侧为 0 时方案二会自动给出 `costBoth × max` 与 `0 × 单品` 的比较结果，不需要特判，但要确认没做除以零或 `min/max` 取反。

## 总结

这类「一件东西同时满足两种需求」的贪心题，标准套路是：先证明最优解里共享品的数量只落在边界上，再把边界情况逐个枚举。三个候选、取最小，比写分类讨论清晰得多；同时别忘了答案量级——`10⁹` 的需求配上 `10⁶` 的单价，一定是 `long long` 的题。

## 复盘

- 我哪里容易想错：一开始容易只算「全单品」和「全组合包」两个极端，漏掉混合方案；也可能在补差额时顺手用了 `cost1`，而实际需求大的可能是类型 2。
- 关键突破点：意识到组合包数量是单调变量——只要它比「一个类型 1 + 一个类型 2」便宜就应当尽量多买，于是最优数量必然卡在 `0 / min / max` 三个边界。
- 下次看到什么特征应该想到这个算法：两类需求 + 一件商品同时满足两类，且要求最小花费——先找「共享品」与「单独买」的价格比较，再对共享品数量取边界枚举。
